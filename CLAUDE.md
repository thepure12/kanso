# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Shared kanban boards: Nuxt 4 + Nuxt UI 4, Postgres 17 with row-level security, Drizzle ORM, `nuxt-auth-utils` (email/password + Discord/GitHub/Google OAuth). Package manager is pnpm.

## Commands

```bash
pnpm install
cp .env.example .env              # NUXT_SESSION_PASSWORD (32+ chars), OAuth keys optional
pnpm db:up                        # docker compose up -d db: Postgres 17; docker/init.sql creates the 3 roles
pnpm db:migrate                   # drizzle-kit migrate as kanban_owner (MIGRATION_DATABASE_URL)
pnpm dev                          # http://localhost:3000
pnpm typecheck                    # nuxt typecheck (vue-tsc)
pnpm build
pnpm test                         # vitest run — all projects
pnpm vitest run --project db      # one project: db | unit | components | api
pnpm vitest run tests/rls.test.ts             # single file
pnpm vitest run tests/rls.test.ts -t 'viewer' # single test by name
docker compose --profile app up -d --build    # db + migrate (one-off) + app on :3000, all in containers
```

Deployment: `Dockerfile` stages `build` (pnpm via corepack, version from `packageManager`), `migrate` (build stage running `pnpm db:migrate`) and `runtime` (node 22 alpine, only `.output`, user `node`, `NODE_ENV=production`). Compose services `migrate` and `app` sit in profile `app`, read `.env` and override the DB URLs to host `db`. Not built locally (no Docker access when written). `docker-compose.prod.yml` is the server stack: no profiles, role passwords from `.env` (`KANBAN_*_PASSWORD`, passed to `docker/init.sql` as psql variables by `docker/init-prod.sh`; without them init.sql keeps the dev passwords), Caddy (`docker/Caddyfile`, `KANBAN_DOMAIN`) is optional, profile `caddy` via `COMPOSE_PROFILES`; the app is published on `KANBAN_APP_PORT` (default `127.0.0.1:3000`) for a host proxy, Postgres never. `deploy/embedded-pg/` (own `package.json`, installed with npm on the server, not part of the pnpm workspace): `start.mjs` runs Postgres 17 from `embedded-postgres` on 127.0.0.1 for servers with neither Docker nor Postgres, and on each start creates the `kanban` database, roles and schema settings of `docker/init.sql` and sets role passwords from env; systemd units in `docs/DEPLOYMENT.md`. `deploy/install.sh`: interactive install/update for a dedicated non-root user (refuses root): `systemd-embedded` | `systemd-pg` | `docker`; systemd user units (`kanso.service`, `kanso-pg.service`, needs `loginctl enable-linger`), files under `~/.local/share/kanso`, settings for re-runs in `~/.config/kanso/install.conf`, writes an Apache snippet; `--dry-run` prints instead, `KANSO_INPUT=<file>` feeds answers in tests. CI: `.github/workflows/ci.yml` runs postgres:17, `docker/init.sql` via psql, `cp .env.example .env`, migrate, typecheck and every vitest project.

Vitest projects (`vitest.config.ts`); `db` and `api` share the database, so their files run serially (`fileParallelism: false`) and `api` runs after `db` (`sequence.groupOrder`); `unit` and `components` run in parallel:
- `db` — `tests/*.test.ts`. Hit the real database (no mocks), connecting as `kanban_app` / `kanban_auth` with URLs from `.env`. Need Postgres running and migrated.
- `unit` — `tests/unit/`: pure helpers in `app/utils/` (markdown test uses jsdom; DOMPurify misbehaves under happy-dom).
- `components` — `tests/components/`: `mountSuspended` in the Nuxt environment. `fsModuleCache` is off for it: the cached test-utils entry stub breaks the next run.
- `api` — `tests/api/`: the project's global setup (`tests/api/build.ts`) builds the app once into `.nuxt/test/api`; each file starts its own server from it with `setupApi(env)` (`tests/api/server.ts`, `@nuxt/test-utils/e2e` with `build: false`), then calls it over HTTP as signed-up users. Uses the global `fetch` with a captured base URL because test-utils' context exists only inside tests. Each user sends its own `x-forwarded-for` to stay under the login rate limit.

## Architecture: Postgres owns authorization

The core design rule: **all permission logic lives in Postgres (RLS policies, `SECURITY DEFINER` functions, triggers). The app holds none.** Do not add role checks in route handlers; add or change policies instead.

Three DB roles (`docker/init.sql`), each with its own connection URL:
- `kanban_owner` — migrations only; owns tables and `app.*` functions. RLS is ENABLEd, not FORCEd, so owner-defined `SECURITY DEFINER` helpers bypass policies (avoids recursion).
- `kanban_app` — all board/card/team requests (`NUXT_DATABASE_URL`). `NOBYPASSRLS`; cannot read `password_hash` or `oauth_accounts`.
- `kanban_auth` — login/register/OAuth callbacks only (`NUXT_AUTH_DATABASE_URL`, via `useAuthDb()`).

Request flow (`server/utils/`, auto-imported by Nitro):
- `defineUserHandler(fn)` (`session.ts`) requires a session (or an API token, see below), then calls `withUser(userId, tx => ...)` (`db.ts`), which opens a transaction on the `kanban_app` pool and runs `set_config('app.user_id', id, true)`. Transaction-local, so pooled connections never leak identity. Every authenticated API route uses this wrapper. It also sets `app.client_id` from the `x-client-id` header (the browser tab), used by board change notifications.
- DB errors thrown by RLS/triggers/constraints are mapped to HTTP errors by `toHttpError` (`errors.ts`): `42501`→403, `P0002`→404 (unknown email), `23514`→409 for the last-owner triggers (no constraint name), 400 for check constraints, `23505`→409 (`data.problem` `nameTaken` only for `*_name_unique`; forms use `isNameTaken`, `app/utils/nameTaken.ts`, never any 409), `23503`/`22P02`→400. An RLS-filtered `UPDATE`/`DELETE` affects zero rows rather than erroring, so handlers use `.returning()` and `notFound(...)` when no row comes back.
- Input validation: zod v4 via `readValidated(event, schema)` (400 whose `statusMessage` names the first issue, e.g. `title: Too big: ...`, issues in `data.issues`; `useApiError` translates known ones) and `paramsValidated(event, uuidParam)`.
- Operations that need privileged lookups go through `app.*` SQL functions called with `tx.execute(sql\`select ... app.fn(...)\`)`: `app.create_board`, `app.add_board_member`, `app.create_team`, `app.add_team_member`, `app.board_role` (effective role = stronger of direct board role and team role).

Other invariants enforced in SQL (see `server/db/migrations/0001_rls.sql`, `0003_teams_rls.sql`):
- A board's team is fixed at creation (column-level `UPDATE` grant on `boards.name` only).
- Triggers keep at least one owner per team and per personal board.
- `cards (column_id, board_id)` has a composite FK to `columns (id, board_id)`, so cards cannot move across boards. Likewise `card_tags` carries `board_id` with composite FKs to `cards (id, board_id)` and `tags (id, board_id)`, so a card only carries tags from its own board.
- Column rules (`column_rules`, `0008`, `0010`, `0012_card_features_rls.sql`): `kind` enum (`apply_tag`, `remove_tag`, `assign_to`, `set_due`, `assign_mover`) plus kind-specific columns (`tag_id`, `user_id`, `due_days`; check `column_rules_kind_fields`). `assign_mover` (`0064`) has none of them and assigns `app.current_user_id()` (whoever creates or moves the card in; nobody for automations; the schedule owner for recurring cards), at most one per column (partial unique index), never applied to existing cards; the UI lists it first in the Assign select. They run when a card is inserted or its `column_id` changes (reorder within a column does not re-run them); a newly added tag/assignee rule is also applied by `POST /api/columns/:id/rules` to the column's current cards (not templates/archived; `set_due` is not): AFTER trigger `cards_apply_column_rules` adds/removes tags and adds assignees (skipping people who lost board access), BEFORE trigger `cards_set_column_rule_fields` sets `due_date` (at most one `set_due` per column). New rule kinds: add to the enum, the check, the matching trigger, `toColumnRule` (`server/utils/rules.ts`) and `ColumnRulesModal.vue`. A migration that adds an enum value cannot use it as a literal in the same transaction (drizzle-kit runs all pending migrations in one), so compare `kind::text` there.

- Board rules (`0095`/`0096_board_rules_rls.sql`, `server/utils/boardRules.ts`, `app/utils/boardRules.ts`): event-triggered "when <event> and <conditions>, do <actions>". `board_rules` (`event` enum `board_rule_event`: card_created, card_moved, tag_added (optional `event_tag_id`), assigned (optional `event_user_id`), due_set, checklist_completed (every item done), commented (not imported); conditions `cond_tag_id`, `cond_priority`, `cond_column_id`, `cond_assignee_id` (all must hold); actions `move_column_id` (end of column, column rules run), `add_tag_id`, `remove_tag_id`, `assign_user_id` (members only), `set_priority`, `set_due_days` (also pulls a later start back), `archive`, at least one (check `board_rules_has_action`; `board_rules_*` checks → 400); composite FKs, deleting a named tag/column/person deletes the rule; `active`, `created_by` = caller). SSE routes push a `ping` at once (h3 sends headers with the first write; never `await` a push before returning `stream.send()`, it waits for the reader), then every 25 s. New board tables need a `*_notify` trigger. Token streams (`0115_activity_events.sql`): `/api/events` is in `tokenRoutes` and takes a Bearer token (any scope; `requireTokenUser`, board limits via `withUser`'s auth), re-checked every 25 s by `apiTokenLive` (`NUXT_EVENTS_TOKEN_CHECK_MS` for tests), closing the stream once it fails. `?activity=<kinds>&columns=<ids>`: trigger `app.notify_card_activity` sends `NOTIFY card_activity {a, b, card, kind, col, c}` (not personal reminders, not same-transaction boards; `onCardActivity` in `realtime.ts`); the stream filters by kind/column, drops entries from its own `clients`, checks `select 1 from card_activity where id = a` under RLS, then sends `activity {a, b, card, kind, column}` per board in order. `change` events are off with `activity` unless `change=1`. Docs: `docs/API.md` "Event stream".

Ordering: cards and columns use fractional `position` (float). `server/utils/position.ts` computes the midpoint between neighbour IDs (`aboveId`/`belowId`, null = start/end) and renumbers the scope in steps of 1024 when the gap gets too small. Clients send neighbour IDs, never raw positions. Exception: `PUT /api/columns/:id/order {cardIds}` renumbers a whole column (every shown card exactly once, else 409; column rules do not run), used by the column menu's "Sort by priority" (`useBoard.sortColumnByPriority`, undoable via `restoreOrder`).

## Sub-path deployments

`NUXT_APP_BASE_URL` (build time; Docker build arg) sets `app.baseURL` in `nuxt.config.ts`, e.g. `/kanso/`. `$fetch`, `useFetch`, `api`, `NuxtLink`, `navigateTo`, assets and Nitro routing follow it (`matchedRoute.path` stays relative). Hand-built URLs must not: use `appUrl('/api/...')` / `basePath()` (`app/utils/basePath.ts`; capture `basePath()` during setup for later callbacks) for EventSource, `<img src>`, `<a href>`, `external` links, `window.location`, and pass it to `backgroundStyle(bg, id, thumb, base)`; server redirects go through `appPath('/login')` (`server/utils/basePath.ts`). OAuth handlers pass `redirectURL: oauthRedirectURL(provider)` (from `NUXT_PUBLIC_SITE_URL`, which includes the path; behind a proxy the request URL is http). PWA manifest uses `baseURL`; workbox `urlPattern`s are serialised into sw.js, so they strip the service worker scope path instead of reading `baseURL`. Under a base path the session cookie is `kanso-session` with `path` = the base.

## Internationalisation

- `@nuxtjs/i18n` (vue-i18n), locales `en` (default) and `de` in `i18n/locales/<code>.json`, lazy-loaded, strategy `no_prefix`. Locale: `users.locale` (null = browser; `GET /api/me`, applied by `layouts/default.vue`; set on `/account`, `PATCH /api/account { locale }`), else cookie `i18n_locale`, else browser. Nuxt UI strings and `<html lang>` follow it (`app.vue`).
- **All UI text goes through i18n**: `const { t, locale } = useI18n()` in components and composables (toasts, labels, placeholders, aria-labels, empty states, `useHead` titles). New strings: add the key to every locale file; `tests/unit/i18n.test.ts` checks same keys, same `{placeholders}` and plural form counts, and that vue-i18n compiles them (escape `@`, `{`, `}`, `|` as `{'@'}`). Counts use plural forms `"one | many"` with `t(key, named, count)`. Keys are grouped by area (`common.*` shared words, `board.*`, `card.*`, ...).
- Dates and numbers: pass the locale (`formatDate(d, locale.value)`, `Intl.*(locale.value)`); never `undefined`. Priority labels are `t('priority.<p>')` (`priorityMeta` has colour/icon only).
- Code shared with the server takes an `I18nContext` (`{ t, locale }`, `shared/i18n.ts`) instead of using vue-i18n: `describeActivity`/`describeNotification` (`activityText.ts`), `formatPoints`, `formatDateRange`. Client: `useI18nContext()`; server: `serverI18n(locale)` (`server/utils/i18n.ts`, a small formatter over the same JSON; unit tests use it too).
- Server text: mails (`mail.ts`, keys `mail.*`) use `recipientLocale(event, userId)` = `users.locale`, else the request's locale cookie, else en; the digest gets `locale` from `app.claim_digests`; webhook Slack/Discord/json `text` uses the webhook creator's locale (`claim_webhook_deliveries`/`webhook_ping_target` return it, `0043_user_locale_rls.sql`). API error messages stay English.
- New locale: JSON file, `nuxt.config.ts` `i18n.locales`, `locales` in `shared/i18n.ts`, `users_locale_check` (migration), Nuxt UI locale import in `app.vue`, `languageItems` on `/account`.

## Schema changes

Edit `server/db/schema.ts`, then `pnpm db:generate` and `pnpm db:migrate`. Generated migrations contain no RLS: for any new table, add policies and grants (to `kanban_app` / `kanban_auth`) in a custom migration (`pnpm drizzle-kit generate --custom`), and add RLS tests in `tests/`.

## Frontend

- `app/` is the Nuxt 4 app dir; `shared/types/` holds API response types imported via `#shared/types/...` from both sides.
- `app/composables/useBoard.ts` owns board page state and all mutations: optimistic local updates, and on failure a toast (`useApiError`) plus a full `refresh()`. Drag and drop (`vue-draggable-plus`) updates per-column lists first, then `cardMoved`/`columnMoved` persist using the neighbours in the new order. It also subscribes to the board's live events (`useLiveEvents`) and refreshes on `change`, deferring while a drag or mutation is in flight; `remoteVersion` tells open dialogs to refetch.
- Undo (`app/composables/useUndo.ts`: generic stack, limit 20, `group()` merges entries into one step): `useBoard` records an inverse (and redo) after each successful undoable mutation via `record(label, undo, redo)`, which shows a 6 s "<label> · Undo" toast. Inverses look things up by id at undo time (board reloads replace objects) and go through the API, throwing when the target is gone; failures toast "Couldn't undo" and `refresh()`. Moves capture the old neighbours (drag order snapshot when `dragging` turns true, or before `moveCard`) and are placed back next to whichever still exist. Undoable: card/column moves, archive, `updateCard` (changed keys only, not templates), column title/colour/WIP, tag edits, field values; `useCardDetail` records checklist item deletes through the injected `boardUndoKey`. Card delete moves the card to the trash without asking (undo restores it); creates and other hard deletes are not undoable. Ctrl/Cmd+Z / Shift+Z in the board page. New undoable mutations: capture the old state before the optimistic change, call `record` after the API succeeds.
